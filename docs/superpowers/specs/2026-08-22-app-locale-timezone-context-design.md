# App 向前端传递语言与时区设计

## 背景与目标

BitPongo 移动端使用内嵌 WebView 承载前端页面，双方已经通过 `getContext` 命令传递 App 版本、平台、系统版本和安全区。本次在不破坏旧版 App 与新版前端组合的前提下，扩展该上下文，使 App 为前端提供用户设备的默认语言和当前时区。

语言只作为首次默认值：用户在前端手动选择过语言后，前端保存的选择始终优先。时区没有独立的前端人工设置入口，因此每次启动都以 App 当前值刷新，以适应旅行、系统设置变化和夏令时切换。

本次仅修改 `/Volumes/ExternalDrive/Code/github/bitpongo-mobile` 和 `/Volumes/ExternalDrive/Code/github/bitpongo-front`，不修改任何 `zhitoubao` 目录，也不修改后端 API。

## 方案比较

### 方案 A：扩展现有 `getContext`（采用）

在现有响应中增加可选的语言、IANA 时区和 UTC 偏移字段。前端在挂载应用前读取上下文并应用默认值。

优点是沿用现有受控桥接协议、来源校验和测试结构，不在 URL 中暴露环境信息，也能在首屏渲染前确定语言。新增字段保持可选，可兼容旧版 App。

### 方案 B：通过 URL 查询参数传递

实现简单且同步，但语言和时区会进入地址、日志和分享链接；页面内部导航还需要持续保留参数。本次不采用。

### 方案 C：页面加载后由 App 主动执行 JavaScript 注入

无需前端主动拉取，但容易出现初始语言闪烁，并增加 WebView 生命周期和重复注入的时序处理。本次不采用。

## 桥接协议

保持现有 `getContext` 命令、请求响应信封和桥接版本不变，在 `NativeContext` 中增加以下可选字段：

```ts
interface NativeContext {
  appVersion: string;
  platform: 'android' | 'ios';
  systemVersion: string;
  safeArea: {
    top: number;
    right: number;
    bottom: number;
    left: number;
  };
  locale?: 'zh-cn' | 'zh-tw' | 'en-us';
  timeZone?: string;
  timeZoneOffsetMinutes?: number;
}
```

- `locale` 使用前端现有的规范化语言标识。
- `timeZone` 使用 IANA 时区名称，例如 `Asia/Shanghai`。
- `timeZoneOffsetMinutes` 表示当前本地时间相对 UTC 的分钟偏移，例如上海为 `480`。

字段保持可选，使新版前端能继续运行在尚未升级的旧版 App 中。新版 App 应始终提供这三个字段。前端只接受支持的语言值、非空时区字符串和有限数值；缺失或无效字段进入降级流程。

## App 端设计

`AppContextService` 继续负责构建桥接上下文，并新增可注入的语言、时区和偏移读取器，便于单元测试使用确定数据。

语言取自 Flutter 当前系统区域设置，并映射为前端已有的三种语言：

- 中文且脚本为 `Hant`，或地区为 `TW`、`HK`、`MO`：`zh-tw`。
- 其他中文，包括脚本 `Hans` 及地区 `CN`、`SG`：`zh-cn`。
- 非中文语言：`en-us`。

IANA 时区由 `flutter_timezone` 获取；当前 UTC 偏移由 `DateTime.now().timeZoneOffset.inMinutes` 获取。读取时区失败时，App 不应阻断 WebView 启动，而是省略无效字段，让前端使用浏览器降级值。桥接命令和已有安全区计算保持不变。

## 前端启动与优先级

前端增加应用上下文初始化模块，并在 Vue 应用挂载前调用。初始化顺序如下：

1. 通过现有 `getNativeContext()` 获取 App 上下文。
2. 若本地不存在有效的 `lang`，使用 App 返回的有效 `locale` 作为默认语言。
3. 若本地已经保存有效的 `lang`，不允许 App 值覆盖它。
4. 每次启动使用 App 返回的有效时区和偏移刷新本地应用上下文。
5. App 上下文缺失或桥接不可用时，语言继续沿用当前前端规则；时区使用浏览器 `Intl.DateTimeFormat().resolvedOptions().timeZone` 和当前日期的 UTC 偏移降级。
6. 完成初始化后再安装国际化插件并挂载应用，避免首屏先显示错误语言再切换。

时区存储与读取集中在应用上下文模块中，不散落到页面。建议使用独立键保存 `timeZone` 和 `timeZoneOffsetMinutes`。当前业务仅建立 App 到前端的传递与读取能力，不新增 API 请求头，不自动修改用户资料，也不改变后端数据库字段。

桥接调用失败、超时或返回部分字段时均不得阻止页面启动。旧版 App 下语言行为与当前版本一致，时区退回浏览器值。

## 兼容性与安全

- 新版前端 + 旧版 App：新增字段缺失，按浏览器路径降级。
- 旧版前端 + 新版 App：旧前端忽略响应中的额外字段。
- 新版前端 + 新版 App：应用新的语言默认值和时区。
- Web 浏览器：桥接不存在时保持可用。
- 不重命名现有原生桥接对象和 JavaScript 回调，避免破坏已经发布的兼容约定。
- 不信任未经校验的桥接值；无效语言不写入 `lang`，无效时区不覆盖有效的降级值。

## 测试策略

采用测试先行，覆盖以下行为：

### 移动端

- 简体中文、繁体中文和非中文区域设置的映射。
- `AppContextService` 输出规范化语言、IANA 时区和分钟偏移。
- 时区读取失败时仍能返回其余上下文。
- `getContext` 桥接响应包含新增字段，其他命令和错误响应不变。

### 前端

- 本地没有语言时采用 App 默认语言。
- 已手动保存的有效语言优先于 App 语言。
- App 返回不支持的语言时不污染本地设置。
- App 时区在每次初始化时刷新。
- 旧版 App 缺少字段、桥接失败和普通浏览器环境均能正常降级。
- 现有桥接、国际化和页面测试继续通过。

完成实现后分别运行前端单元测试、类型检查和生产构建，以及 Flutter 单元测试和静态分析。若本机原生构建环境无法完成 Android 或 iOS 构建，应明确区分已通过的 Dart/前端验证与未执行的原生构建。

## 验收标准

- 新安装或未选择过语言的用户首次打开 App 时，前端使用设备对应的受支持语言。
- 用户在前端切换语言后，后续启动不被 App 默认语言覆盖。
- 前端能够读取 App 提供的 IANA 时区和当前 UTC 偏移，并在每次启动时更新。
- 旧版 App、普通浏览器以及时区插件读取失败时页面仍能正常启动。
- 不修改后端协议，不修改任何 `zhitoubao` 目录，不覆盖两个仓库中用户已有的未提交改动。
