# 注销账号页面与接口修复设计

## 背景

当前账号设置页使用大块警告卡和三条后果列表，文案密度及红色强调程度与登录、注册、我的页面不协调。注销请求本身还存在一个前后端契约问题：当前密码错误时，后端返回 HTTP 401，前端全局拦截器会把它当作登录失效并强制退出，导致用户无法留在页面重试。

## 目标

- 将注销页改成与注册页接近的普通表单布局。
- 将风险说明压缩为一段简短文案，移除三条后果列表。
- 保留密码确认、明确勾选、二次确认弹窗和失败重试能力。
- 当前密码错误返回 HTTP 400，不触发全局登录失效逻辑。
- Token 无效、账号不存在或已注销仍返回 HTTP 401。
- 不改变实际注销的数据处理流程。

## 前端设计

页面使用全局暖白背景和 `1.25rem` 页面内边距，不再显示独立白色警告卡。内容顺序为：

1. 页面标题。
2. 一段灰色风险说明。
3. 当前密码输入框。
4. 明确确认复选框。
5. 红色的确认注销按钮。

标题、说明、输入区间距及字号与注册页保持同一层级。红色只用于危险操作按钮和必要错误反馈，不把整块内容渲染成警告色。

简体中文文案：

- 标题：`注销账号`
- 说明：`注销后，账号及相关数据将无法恢复。`
- 密码标签：`当前密码`
- 密码占位：`请输入当前密码`
- 确认项：`我已了解并确认注销账号`
- 按钮：`确认注销`
- 弹窗标题：`确认注销账号`
- 弹窗内容：`账号注销后无法恢复，确定继续吗？`

繁体中文和英文使用相同语义同步精简。删除不再使用的三条后果说明语言键，其他注销语言键保留。

交互流程不变：密码非空且勾选确认后按钮才可用；点击后展示二次确认；成功后清除本地会话并跳转登录页；失败时保留密码和页面状态以便重试。

## 后端接口设计

接口保持 `DELETE /api/users/account`，请求体仍为 `{ "password": "..." }`，成功响应保持不变。

`AccountDeletionService` 在登录用户输入错误当前密码时抛出业务码 400，而不是 401。原因是当前会话认证仍然有效，失败的是危险操作的二次密码确认。全局异常处理器据此返回 HTTP 400，前端只显示错误信息，不清空会话。

账号不存在、非 active 状态或 Bearer Token 无效的行为不变，继续由认证链路返回 HTTP 401。

事务内的现有行为不变：停止策略、清除交易所凭据、匿名化用户、将账号标记为 deleted，并在提交后暂停调度。计划执行入口仍以 active 状态为保护条件。

## 范围边界

- 不更改注销 URL、请求体或成功响应。
- 不改为物理删除用户和历史数据。
- 不调整其他账号接口或全局 401 拦截逻辑。
- 不修改旧 `zhitoubao` 仓库。
- 按用户要求只交付修复代码；发版测试由用户执行。

## 验收标准

- 注销页不再显示三条后果列表和大块警告卡。
- 三种语言的注销文案语义一致且简洁。
- 密码错误时后端响应 HTTP 400，前端不会被全局 401 逻辑强制退出。
- 真正的未认证请求仍响应 HTTP 401。
- 前端与后端分别提交到各自 `main`，最终工作区干净。
